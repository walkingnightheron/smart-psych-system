## 2. 教学模拟问卷计分规则

### 2.1 固定配置

| 规则项 | 教学模拟卷配置 |
| --- | --- |
| 题量与题型 | 6 道必答单选题，选项 `A/B/C/D` 分别对应原始分 `1/2/3/4` |
| 维度 | `STRESS`：Q1、Q2；`MOOD`：Q3、Q4；`SLEEP`：Q5、Q6 |
| 正反向 | Q1、Q2、Q3、Q5 正向；Q4、Q6 反向 |
| 正向有效分 | `effective = raw`，统一保留两位小数 |
| 反向有效分 | `effective = reverseMaxPlusMin - raw = 5 - raw`；所以 A/B/C/D 分别为 4/3/2/1 分 |
| 维度公式 | 三个维度均 `SUM` |
| 总分公式 | `SUM`，六题有效分之和；因此本模拟卷中三维度分之和必等于总分 |
| 理论值域 | 最低 6 分，最高 24 分 |
| 区间 | `GOOD 状态良好 [6,10]`；`MILD 轻度压力 [11,15]`；`MODERATE 中度困扰 [16,20]`；`HIGH 重点关注 [21,24]`，均为闭区间 |
| 规则版本 | `R-2026.1`；结果须透传规则版本和非空建议 |

引擎同时支持的其他配置在独立用例覆盖：总分 `AVG` 为全部有效分之和除以已答题数并 HALF_UP 保留两位；维度可独立 `AVG`；总分 `SUM_DIMENSIONS` 为维度分之和；反向基数缺省时回退为该题选项 `max+min`；区间可按 `minInclusive/maxInclusive` 排除端点，空档返回 `UNCLASSIFIED`。

## 5. 真实缺陷复现、定位、修复与回归闭环记录

> 四项均来自本项目跨代理审阅/联调过程中遇到的真实工程问题。这里保留“现象 → 根因 → 修复 → 回归证据”，便于成员写入个人实训工作单；不将推测包装成新发现。

### DEF-01：`seed.sql` 口令哈希与统一口令不一致

| 环节 | 记录 |
| --- | --- |
| 复现 | 使用 seed 声称的统一口令 `123456` 登录种子账号失败；当时 SQL 中误用了对应 `admin123` 的 BCrypt 哈希。明文口令与数据库哈希不匹配，BCrypt 校验正常地拒绝登录。 |
| 自动拦截 | `ScoringEngineSevenSamplesTest.seedSqlPasswordHashMatchesPlain123456` 扫描 `seed.sql` 哈希并调用 `BCryptPasswordEncoder.matches("123456", hash)`，发现不匹配后以真实缺陷失败，而不是放宽断言绕过。 |
| 定位结论 | 缺陷位于种子数据，不在登录服务或 BCrypt 算法：明文文档、SQL 初始化和单元测试三者的口令契约不一致；仅靠“哈希格式像 BCrypt”不能证明密码匹配。 |
| 修复 | 将 `seed.sql` 的 7 个模拟账号哈希统一替换为已经验证匹配 `123456` 的标准 BCrypt：`$2a$10$N.zmdr9k7uOCQb376NoUnuTJ8iAt6Z5EHsM8lE9lBOsl7iKTVKIUi`；demo 模式仍通过 `PasswordEncoder.encode("123456")` 独立生成合法哈希。 |
| 回归闭环 | 口令专项测试已包含在 **16/16 通过**中；所有集成用例的 `loginRaw` 均用 `123456` 获取 Token，**22/22 通过**同时证明登录链路恢复。源码证据：`seed.sql` 用户段与两份 Surefire 报告。 |
| 可复用经验 | 对种子数据中的口令、ID、版本和预置分数增加自动校验，不能用“能启动”替代“数据可用”。 |

### DEF-02：PC 工作台缓存观测字段映射偏差

| 环节 | 记录 |
| --- | --- |
| 复现 | 后端 `/api/admin/cache/metrics` 实际返回 `configuredMode/activeBackend/recentEvents`，单个事件字段为 `eventType/timestamp/key/detail`。工作台早期按 `cacheMode/mode/provider` 与 `action/type/event/source` 读取，导致真实后端名称丢失、事件动作退化为 INFO。 |
| 定位结论 | 问题是 DTO 字段契约与 Vue 规范化函数不一致，不是缓存没有 HIT/MISS/EVICT，也不是计数接口异常。 |
| 修复 | `DashboardView.vue` 新增/完善 `formatCacheMode`：优先使用 `activeBackend`，将 `MEMORY_FALLBACK` 明示为“内存降级缓存”并附带 `configuredMode`；`normalizeEvents` 优先读取 `eventType`，同时支持 `recentEvents` 并补充 PUT 标签，时间使用 `timestamp`。 |
| 回归闭环 | `req09_firstReadMissesSecondReadHits` 证实后端确实输出 HIT/MISS、指标和事件；PC 规范化逻辑按同一真实 JSON 可分别还原运行后端、HIT/MISS_DB/PUT/EVICT 和时间。两端的 39 项报告保持通过；答辩走查时应现场查看面板而非只看代码。 |

### DEF-03：PC 活动详情抽屉缺少名单交卷状态聚合

| 环节 | 记录 |
| --- | --- |
| 复现 | 活动详情接口的 `participants` 是用户资料列表，早期抽屉仅展示学号/姓名/班级。虽然活动已有完成数和统计报告，“交卷状态/交卷时间”列无法准确区分各学生。 |
| 定位结论 | 两个接口职责不同：`GET /activities/{id}` 给基本配置与名单，`GET /activities/{id}/statistics` 的 `participantDetails` 才有 submitted/submittedAt/taskStatus 等；页面只取了前者。 |
| 修复 | `ActivityView.vue` 新增 `activityStats`，详情抽屉打开时用 `Promise.all` 并发取详情和统计；以 `userId` 优先、`username` 兜底合并 `participantDetails`，再展示已交卷/待作答和交卷时间，保留无统计时使用基础名单的退路。 |
| 回归闭环 | 按活动 1 种子数据回核名单：`20260001`、`20260002` 为已交卷并带原提交时间，`20260003` 为待作答；第三人提交后统计接口和抽屉可同步成 3/3。后端统计正确性由 `req07_threeRosterTwoSheetsYields66_67Completion` 及 `req08_pendingAndFailedReportsExcludedFromLevelDistribution` 已执行断言支撑。 |
| 可复用经验 | 页面聚合应以真实 VO 字段和稳定键合并；不要给 UserVO 硬塞报告状态，也不能用总人数替代逐人状态。 |

### DEF-04：AFTER_COMMIT 投递失败记录缺少独立事务保护

| 环节 | 记录 |
| --- | --- |
| 复现/风险定位 | 提交事务成功后才监听 `AFTER_COMMIT` 是正确第一步，但早期 `ReportTaskDispatcher` 在捕获 MQ 异常后直接调用 Repository 写 `last_error`。在外围事务已完成或被标记 rollback-only 的场景，这次写入可能受原事务上下文影响并再次失败，导致“答卷保留但异常原因没留下”。 |
| 根因 | 错误留痕和原业务事务缺少明确传播边界；同时如果在同 Bean 内自调用 `@Transactional(REQUIRES_NEW)`，代理也不会生效。 |
| 修复 | 新增独立 Spring Bean `DispatchErrorRecorder`，其 `record` 明确标注 `@Transactional(propagation=Propagation.REQUIRES_NEW)`；`ReportTaskDispatcher` 通过代理注入调用，不依赖同类自调用。错误记录自身失败另捕获并记日志，避免二次异常掩盖最初 MQ 投递异常。 |
| 回归闭环 | `req10_sendFailureKeepsSheetAndRecordsLastError` 注入发送失败后，答卷 1 行、明细 6 行保留，报告 PENDING、retry=0、totalScore=null，`last_error` 含“MQ消息投递失败”，管理端报告与统计可查，复位后重试 SUCCESS；包含在 **22/22 通过**中。代码证据：`mq/DispatchErrorRecorder.java`、`mq/ReportTaskDispatcher.java`。 |
| 可复用经验 | 说明 AFTER_COMMIT 时不能只背“提交后投递”，还要回答“提交后的异常记录在哪一个事务里、Spring 代理如何生效、二次异常如何隔离”。 |
